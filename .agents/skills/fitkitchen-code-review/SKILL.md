# FitKitchen code review

Review actual code, callers, and failure paths before drawing conclusions. Use this skill for requested code reviews and implementation self-review. A review request alone does not authorize edits, publishing comments, resolving threads, pushing, or merging; follow the user's authorized scope.

The approach follows [Veritas Review](https://github.com/veritas-living/rental-platform/blob/main/.agents/skills/veritas-review/SKILL.md), adapted to FitKitchen's two application directories. The instructions below are self-contained; the reference repository is not a required dependency.

## Workflow

1. Establish the requested scope and base/head. Read `AGENTS.md`, applicable nested instructions, relevant Markdown docs, and the full diff, including new files, configuration, tests, and lockfiles. For stacked PRs, compare against the actual PR base and inspect compatibility with its dependencies. Keep baseline defects separate from regressions.
2. Identify the affected runtime paths from the current code. FitKitchen has a CommonJS JavaScript Express backend using `pg`/PostgreSQL and a React/TypeScript frontend using TanStack Router/Start, Tailwind v4, and Zustand. Verify these facts against manifests as the project evolves. Existing code establishes current behavior; requirements establish intended behavior. Do not invent missing contracts, test suites, infrastructure, or completed features.
3. Select the **union of all matching checks** below by behavior as well as path. Configuration, tests, wrappers, and shared helpers trigger the production checks for the boundaries they affect. A frontend HTTP helper needs parsing/error checks even when no endpoint changes; a backend address update needs both validation and transaction/concurrency checks.
4. Trace input → validation/authorization where applicable → state mutation → persistence/external output → error handling → cleanup. Inspect a direct caller, relevant guards, the error mapper, and the owner of affected resources/state before reporting a missing safeguard. Look across frontend/backend only when a real call connects them; storefront flows may use Shopify instead of the Node backend.
5. Read relevant tests and verify what they prove. Distinguish unit behavior from real database rollback, concurrency, HTTP integration, and browser evidence. Run proportionate checks when possible. Record each selected check as PASS, FINDING, NOT VERIFIED, or N/A with evidence or a reason; summarize relevant results rather than dumping every inapplicable row into the response.
6. Challenge each proposed finding against callers, guards, constraints, requirements, and tests. State a reachable input, failure, or interleaving and its impact. Drop findings ruled out by surrounding code. Separate confirmed defects from inferences and open questions. Zero findings is a valid result.
7. Report findings by impact, then verification and limitations. If fixes were requested, make the smallest in-scope correction and recheck the affected path. Keep screenshots, generated review reports, and other temporary evidence out of commits; report results directly in the PR description or response.

## Choose checks by changed behavior

| Change                                                                 | Apply                                                                          | Read in this repository                                                                                        |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Runtime code, configuration, dependencies, or tests                    | Applicable common checks plus affected stack checks                            | Root/nested `AGENTS.md`, relevant source, manifests, callers, tests                                            |
| `backend/src/**`, including routes/controllers/validation/services     | Common + backend                                                               | `backend/src/app.js`, affected module in `backend/src/modules`, database configuration, `backend/package.json` |
| `frontend/src/**`, including stores, hooks, routes, clients            | Common + frontend                                                              | `frontend/AGENTS.md`, affected component/store/client and its callers, `frontend/package.json`                 |
| Request/response fields, enums, errors, URLs, or units                 | Common boundary/error/compatibility checks + both actual producer and consumer | Actual routes/validators/queries and client adapters; requirements and schema when relevant                    |
| Database writes, initialization SQL, or Compose/database configuration | Common + backend transaction/configuration checks                              | `backend/db/init`, `backend/docker-compose.yml`, affected `pg` calls                                           |
| Rendered UI, shared primitives, tokens, copy, or responsive layout     | Frontend checks + [fitkitchen-ui-review](../fitkitchen-ui-review/SKILL.md)     | [Design system](../../../docs/design/DESIGN_SYSTEM.md), actual components and rendered screens                 |
| Documentation or skills only                                           | Documentation accuracy and artifact-scope checks                               | Referenced paths, actual commands/components, skill frontmatter/links                                          |

Discover actual paths with `rg --files` instead of assuming files or methods exist. Preserve the frontend Lovable-managed block, generated-file boundaries, and published Git history. A review must not expand into building authentication, RBAC, JWT, Admin APIs, or infrastructure that the task does not request.

## Common checks

| ID / Trigger                                               | Check                                                                                                                                                                                                                                                                                                                              | Evidence to seek                                                                                                                                              |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C01 Requirements, state, or ownership                      | Does the change preserve the intended behavior, data owner, and feature scope? Keep live storefront/cart data separate from Admin demos and client-side previews.                                                                                                                                                                  | Requirements, direct callers, authoritative data sources, and before/after behavior.                                                                          |
| C02 Input/output boundary or compatibility                 | Validate runtime input; a TypeScript type/cast does not validate JSON. Check missing/null/empty/malformed values, identifiers, unknown fields, PATCH omission versus explicit clearing, status values, money/currency, kcal/g, and preservation of `0`/`false`. Decode responses once and preserve existing consumers.             | Real adapters, validators, schema constraints, and affected consumers; concrete boundary examples.                                                            |
| C03 Catch, fallback, response, or logging                  | Do not hide failures behind empty lists, success responses, or invalid-credential messages. Map errors at their owning boundary; preserve useful sanitized diagnostics without leaking raw SQL, stacks, credentials, bodies, or personal data.                                                                                     | Injected failure, resulting HTTP/UI outcome, side effects, and serialized/logged error shape.                                                                 |
| C04 Sensitive read/write or identity                       | Check authorization and resource ownership before sensitive effects, including address ownership and writable roles. Inspect existing guards and actual exposure; do not confuse a frontend navigation guard with server authorization or presume an unimplemented auth system exists.                                             | Caller/guard chain and concrete anonymous, foreign-owner, or privilege-changing requests where applicable.                                                    |
| C05 SQL, URL, shell, or filesystem sink                    | Bind SQL values and allowlist dynamic identifiers/sort fields. Validate destination/origin/redirect handling after URL normalization. Avoid unsafe shell/path interpolation and forwarding credentials to unintended origins.                                                                                                      | Attacker-controlled input traced to the actual sink, including malformed IDs, separators, or URLs.                                                            |
| C06 Async work, state, retries, or resources               | Account for stale results, duplicate requests, concurrent writers, rejected promises, and cleanup. Timeouts must address late work; retries need a bound and safe replay semantics. JavaScript's event loop does not prevent races across awaits or database clients.                                                              | A concrete interleaving, rejected callback, timeout plus late completion, and resource lifecycle.                                                             |
| C07 Lists, batches, uploads, caches, or expensive work     | Bound queries, response sizes, concurrency, and retained state where needed. Avoid collecting everything before slicing or launching an unbounded Promise.all. Tie performance claims to a measured or demonstrable path.                                                                                                          | Worst-case rows/bytes/in-flight work, query shape, allocation or event-loop behavior.                                                                         |
| C08 Functions, modules, constants, or refactors            | Prefer existing helpers and clear ownership. Refactors should remove complexity, not move it behind wrappers. Avoid unrelated branches, speculative abstractions, unsafe casts, giant constants files, and duplication that can drift. Preserve operations with different semantics even if their implementations currently match. | Actual references, signatures, duplicated policy/wire values, and observable behavior. Local one-off copy/test data is not automatically a constants problem. |
| C09 Configuration, dependency, schema, or generated output | Review manifests with lockfiles and relevant release notes when dependencies change. Keep secrets out of committed artifacts; distinguish intended public browser configuration from private credentials. Preserve defaults without turning them into undocumented constraints. Do not hand-edit generated files or weaken checks. | Configuration precedence, relevant environment names without exposing values, lockfile/source diffs, and startup behavior.                                    |
| C10 Tests, documentation, skills, or completion claims     | Verify that commands, paths, components, and feature claims exist. Do not mark missing/skipped tests as passed, rewrite expectations to match a bug, or present fixtures as production evidence. Keep Markdown in English and exclude temporary artifacts from PRs.                                                                | Current-head results and referenced source; skill validation and link checks for documentation-only changes.                                                  |

## Express / PostgreSQL backend checks

| ID / Trigger                                            | Check                                                                                                                                                                                                                                                                                                                         | Evidence to seek                                                                                                                          |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| B01 Routes, controllers, or validation                  | Trace registration from `app.js` through the module router/controller to validation and service. Check route ordering, supported methods, ID/filter/body parsing, partial updates, and exactly one response/error path. Validate before effects and map not-found/conflict/internal failure consistently with the actual API. | Requests through the real route stack where feasible; invalid input, missing rows, database failure, and response shape.                  |
| B02 SQL construction or writable fields                 | Values use `pg` parameters; interpolated column names come from an allowlist or validated projection, not arbitrary request keys. Do not return password hashes or accept privileged fields without the applicable policy.                                                                                                    | Every path into the query builder, validated field sets, returned columns, and ownership predicates.                                      |
| B03 Multi-step writes or invariants                     | Use one checked-out client for every statement in a transaction, not `pool.query` inside an unrelated client transaction. Check commit/rollback and release on success, failure, and early returns. Preserve the original failure if cleanup fails.                                                                           | Actual client ownership and failure paths; real disposable-database rollback tests when transaction guarantees change.                    |
| B04 Read-modify-write, uniqueness, or default selection | Write an interleaving for concurrent requests and identify the protecting constraint, row lock, or atomic query. Check empty-result races and default-address consistency. A process-local lock or mocked transaction does not establish multi-client safety.                                                                 | Two competing clients/requests against a disposable database, or the exact database invariant and reachable gap.                          |
| B05 Async handlers, background callbacks, or startup    | Await/return work or provide an explicit terminal error policy. `void promise` is not rejection handling. Check startup failures and resource shutdown only where the change affects them; avoid blocking synchronous work in request paths.                                                                                  | A rejected operation/callback, actual response or process outcome, and pool/timer/listener ownership.                                     |
| B06 Schema/bootstrap/Compose changes                    | Keep SQL assumptions and service queries compatible. Initialization scripts may run only on a fresh database volume; editing bootstrap SQL does not prove an existing database upgrades safely. Review constraints, defaults, data retention, and the actual deployment/update path.                                          | Existing-volume versus fresh-volume behavior; schema/query comparison and disposable-database checks. Never reset shared data for review. |

## React / TypeScript frontend checks

| ID / Trigger                                        | Check                                                                                                                                                                                                                                               | Evidence to seek                                                                                                                             |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| F01 Effects, hooks, stores, or asynchronous state   | Keep state/workflow ownership clear. Check dependencies, cleanup, stale responses after unmount/account changes, duplicate submission, and listener/timer removal. Preserve pending/error recovery rather than optimistic success with no rollback. | Deferred response or failure after a state change, cleanup paths, and actual store consumers.                                                |
| F02 HTTP/Shopify adapters, parsing, or errors       | Check HTTP failures and payload-level errors, decode once, validate necessary runtime assumptions, and keep error details sanitized. Preserve the actual producer's contract rather than assuming the Node backend serves every frontend flow.      | Adapter calls with successful, malformed, empty, and failed responses; resulting state and visible error.                                    |
| F03 Meals, customization, cart, checkout, or plans  | Keep prices/currency/quantities/macros and selected variants accurate. Derive checkout links from real Shopify cart responses; preview-only estimates or demo meals must not become real cart items or invented subscription purchases.             | The actual cart/selection state and outgoing mutation/checkout response; zero, unavailable variants, duplicate clicks, and failed mutations. |
| F04 Routes, browser/server code, or browser storage | Follow TanStack Router/Start conventions and preserve `__root.tsx`'s Outlet. Check SSR versus browser-only access, hydration-sensitive values, client/server boundaries, URL safety, and any credentials written to browser storage or bundles.     | Route registration, SSR/render path, module imports, storage writers, and outbound destinations. Do not manually edit `routeTree.gen.ts`.    |
| F05 UI/components/tokens/content                    | Apply [fitkitchen-ui-review](../fitkitchen-ui-review/SKILL.md) rather than duplicating its 35-item checklist. Reuse domain/shared components and primitives; inspect actual desktop/mobile states and accessibility relevant to the diff.           | Design-system source, rendered behavior, keyboard/focus and applicable data states. Without browser access, mark visual checks NOT VERIFIED. |

## Verification proportional to the change

Read both package manifests before choosing commands; recheck this list if scripts change.

- **Frontend:** `npm run test`, `npm run lint`, and `npm run build` exist. Local `./node_modules/.bin/tsc --noEmit` performs typechecking; there is no `typecheck` script. Check formatting with local Prettier on changed files; avoid `npm run format`, which writes across the repo. Preserve the Bun lockfile and its documented installation workflow.
- **Backend:** `npm start` and `npm run dev` start the server and require appropriate database configuration; they are not tests. The current `npm test` script deliberately exits with “no test specified,” so report the missing suite instead of claiming a backend test pass. There are no configured backend lint/build/typecheck scripts. `node --check <changed JS file>` checks syntax only; API/database behavior needs an appropriate disposable setup or must remain NOT VERIFIED.
- **Documentation/skills only:** validate Markdown, skill frontmatter, referenced paths, examples, and commands. Do not rerun application checks merely to imply runtime coverage for wording changes.
- Record exact commands, directory, outcomes, and unrun checks. If a failure appears to predate the change, reproduce it at the base with equivalent dependencies/configuration without overwriting anyone's work. Do not lower gates, remove assertions, skip tests, install new tooling, or run shared-database mutations just to obtain a passing review.
- Choose regression evidence for changed behavior and risk. When assessing test adequacy, a narrowly scoped negative probe in an isolated copy may help; do not mutate a shared working tree, run destructive database probes, or add tests that only mirror a presentational change.

## Findings and conclusion

Each finding needs a **[P0–P3] title**, minimal `file:line` location, checklist ID, confidence, concrete trigger/input/interleaving, incorrect behavior and user/system impact, evidence, smallest appropriate remedy, and a way to verify the remedy.

- **P0:** immediate, demonstrated exposure or severe data loss requiring urgent action; hypothetical risk is insufficient.
- **P1:** reachable authorization bypass, major data loss, or a broken critical workflow.
- **P2:** a correctness, recovery, compatibility, or usability defect with a concrete condition.
- **P3:** an evidenced maintainability improvement or optional refinement. Mark optional style preferences as such; do not elevate them into blockers.

Use CONFIRMED for demonstrated findings and INFERRED when a stated assumption remains. Put unresolved questions and unverified suspicions in limitations, not among confirmed bugs. Distinguish baseline defects from introduced regressions; do not force a finding count or classify every TODO as a blocker.

Report findings first, then selected-check coverage, actual verification, and remaining risks. If none are found, say so within the inspected scope without claiming absolute safety or complete verification. Offer a review conclusion, not an automatic merge or published approval. When authorized to respond to or resolve a review thread, inspect replies and current code; outdated lines or a resolved label alone do not establish correctness or a fix.
