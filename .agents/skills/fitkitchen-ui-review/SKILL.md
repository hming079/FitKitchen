# Review FitKitchen UI

## Workflow and evidence

1. Read `AGENTS.md`, `frontend/AGENTS.md`, and the [design system](../../../docs/design/DESIGN_SYSTEM.md). Identify users, the primary task, real/demo data, primary/secondary actions, diff scope, and comparable screens. Code paths are relative to the repository root.
2. Inspect the code: tokens in `frontend/src/styles.css`, primitives in `frontend/src/components/ui`, domain/shared components, and data sources. Correct tokens/primitives are insufficient on their own: ask whether each component is necessary to complete the task.
3. Run the app and inspect desktop/mobile output; record viewport, theme, route, and state. Check density, hierarchy, long content, zoom/reflow, overflow/truncation, and relevant tables/forms/dialogs/sidebars. Use the keyboard to inspect focus and navigation order. Check loading/empty/error/success/disabled states when the flow supports them; identify any test fixtures explicitly. Screenshots may support local review, but keep temporary screenshots and verification reports out of commits; record results in the PR description or response.
4. Check every item 01–35 below against code **and**, where possible, rendered UI. Measure the color pairs in use, including hover/focus; token names do not prove readability. Check reduced-motion preferences when animations exist. If no browser is available, continue the code review and clearly identify what remains visually unverified.
5. Fix in-scope issues, inspect the result again, and run relevant repository checks. Report findings and limitations using the format at the end of this file. Do not substitute “clean, beautiful, professional” for evidence.

In the tables, **Signal** describes what to detect, **Ask** is the concrete review question, **Remedy** describes how to address an issue, and **Exception** requires evidence from the actual context. Cards, icons, badges, and motion are not inherently wrong.

## Report findings

For each finding, record:

```text
[Critical | Needs improvement | Suggestion] — #item — short description
Location: route/component/file:line or local screenshot + viewport/theme/state
Evidence: specific code or rendered observation, not speculation
Impact: effects on readability, actions, data integrity, or consistency
Recommendation: a concrete fix or simplification
Recheck: actions performed and results, or what remains unverified and why
```

- **Critical:** prevents the task, misrepresents data/consequences, or hides essential information. **Needs improvement:** harms usability or system consistency. **Suggestion:** a useful refinement that does not block the task.
- When retaining a suspicious-looking pattern, record the item number, location, and evidenced business/interaction reason.
- Include a scope matrix: route × viewport × theme × state; distinguish code inspection from rendered review. Use “checked,” “not applicable — reason,” or “unverified — reason”; do not mark unobserved behavior as passing.
- No findings within the observed scope does not establish application-wide accessibility or complete dark-mode support. Report out-of-scope risks instead of silently expanding the task.
